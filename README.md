# grill-room

Self-hosted rooms for grill sessions. Guests join from an invite link with a display name, no account. The first join gives the browser a lightweight profile that follows its person from room to room. The room shows who is in, a live message stream and the room's documents.

This is an early PoC. `INTENT.md` has the design and `specs/001-grill-room-poc.md` the plan.

## Run

Go 1.27 or newer, and a PostgreSQL 16 or newer database with `C` collation. Create it as its own role, which owns it; the server needs no superuser:

```sql
CREATE ROLE grill_room LOGIN PASSWORD '...';
CREATE DATABASE grill_room OWNER grill_room TEMPLATE template0 LC_COLLATE 'C' LC_CTYPE 'C' ENCODING 'UTF8' LOCALE_PROVIDER libc;
```

For a throwaway one, `make pg-up` (see Make targets) starts a PostgreSQL container on loopback.

```sh
make build
# sslmode=verify-full for any database not on loopback or a private pod network
export GRILL_ROOM_DATABASE_URL='postgres://grill_room:...@db.example:5432/grill_room?sslmode=verify-full'
./bin/grill-room
```

On first start the server logs an `admin_token_generated` line holding the admin token. It is shown once: the database keeps only its hash. Set `GRILL_ROOM_ADMIN_TOKEN` to pin a token instead. To get a new one, delete the `admin_token_sha256` row from `settings` and restart.

### Copying a SQLite database

Servers from before spec 017 kept their data in one SQLite file. `grill-room db copy --from <file> [--to <dsn>]` copies it into an empty PostgreSQL database, `GRILL_ROOM_DATABASE_URL` by default, in one transaction. Every id stays. The copy prints each table's row count and sha256 on both sides and commits only when they all match. It refuses a target that does not sort as `C` or whose schema is not empty, a source at another schema version than the last SQLite server's (46), and a source whose `-wal` file is not empty: copy from a backup taken with the server stopped, then checkpointed. `grill-room db verify` with the same flags runs the comparison again and writes nothing. Both exit 0 when equal, 1 on a refusal, an error or a difference, 2 on a usage error.

Do not start the server on the target first: its first start creates the schema, and the copy then refuses the database. [docs/cutover.md](docs/cutover.md) is the lab's runbook, rollback included.

## Admin page

`/admin` asks for the admin token once (on a restricted instance with an admin group, for the provider's sign-in instead) and then works on a session cookie: HttpOnly, SameSite=Strict, Secure over https, sent only to `/api/admin/`, valid 12 hours. The database keeps only the session token's hash. The page lists the open sessions with their IP and browser, and revokes any of them; a revoked browser gets a 401 on its next request and lands back on the sign-in card. Revoking a provider admin session ends that page's session only: while its last sign-in held the admin group, it can sign in again through the provider. To keep someone out now, delete the profile; removing the group at the provider takes effect at their next sign-in, or at the latest when their sign-in expires (`GRILL_ROOM_OIDC_REVALIDATE`). A client IP gets 10 login attempts per 15 minutes, and a success resets its count. The bearer token keeps working for `curl` and scripts, on every admin route. On a restricted instance with `GRILL_ROOM_OIDC_ADMIN_GROUP` set, an internal whose last sign-in held that group skips the form: opening `/admin` opens a session, until the earlier of the 12 hours and the end of its sign-in's revalidation. Everyone else gets "Sign in with <`GRILL_ROOM_OIDC_NAME`>" and no token form: with an admin group set, the page signs admins in by that group only, while the token keeps working on the API. Such a session belongs to its profile, and Sessions names it. Sign out sticks in that browser: it opens no session by itself again. For a signed-in internal outside the group, that button says so, with a "Sign in again" link, instead of going to the provider.

The page has seven views, in a tab bar: Rooms, Profiles, Libraries, Pronunciation, Server, Sessions and Audit. Each is a deep link (`/admin#profiles`; Server is `#instance`), and so is each room and each of its tabs (`/admin#rooms/<room>/invites`). The lists are rows in columns with a ⋯ per row for its actions; on a phone each row is a short card.

- Rooms: name, creation, last line, participants, personas, whether the host's daemon is online and storage used, sortable by any column. The room's name, or its ⋯, opens it in its own view with four tabs. General shows its volume by kind (uploads, revisions, attachments, agent sessions, transcripts, room skills, plugins) and its quota; there the admin renames it, sets its quota or returns it to the default, and deletes it after typing its name. Invites creates and revokes invites. Admins appoints and removes room admins among the participants with a profile, and renames any participant from the row's ⋯. Export exports it. Above the list, "Import a room" previews an archive and imports it as a new room (see Export and import).
- Profiles: the name a profile chose in a room, else the one it last joined with, its email, rooms, skill count (personal ones plus the shared ones it published) and last activity. Deleting a profile leaves its participants in their rooms, detached. Each row also shows how many rooms the profile created against its limit; its ⋯ sets that limit (a number, unlimited, or back to the server's), makes a recovery link, merges it into another profile, or deletes it. This is the only place an email shows, besides its owner's profile page.
- Libraries: persona templates and shared skills, with author and latest version. The admin removes any but the shipped templates.
- Pronunciation: how the call voices say a term (spec 013), searchable. Each term is said English-style or French-style, flipped in one click from its row; its ⋯ edits its three spoken forms or removes it, and "Add a term" adds one, up to 1000. The server ships about 130 terms, inserted once: later edits and removals stand. A change reaches the `tts` pod for its next line.
- Server: server version, database size, free and total space on the disk of `GRILL_ROOM_STAGING_DIR`, speech to text, connected AI host apps by version, and whether SMTP is set. Below, one settings group with one Save: who creates rooms (anyone with a profile, or the admin only), how many rooms a profile may have created (10 by default), and an optional storage quota. Past that quota, which counts the bytes the rows hold, profiles create no room. A server that finds the instance at its quota refuses every room creation (anonymous, from a profile, from a starter, or by import) with the same reason for the next 30 seconds without measuring again; saving the settings clears that on the server that saved them, the others follow within 30 seconds. In the same group, deleting empty profiles is a switch that applies at once.
- Sessions and the audit log, below.

A room's quota counts its uploads and annotation images, the blobs people add. Revisions, transcripts and agent sessions show in its volume but do not count. Only the admin changes a quota; a participant asking through the room's API gets a 403. The volume comes from SQL sums over lengths, so the view reads no blob.

The audit log records every admin action: room create, rename, quota change, export, import and delete, invite create and revoke, room admin appointment and removal, renames of participants by a room admin or the admin, removals of people and lifted blocks, document deletion and restoration, room skill removal, profile delete, merge and rooms limit, the purge of empty profiles (actor `system`), template and skill removal, room creation limits, lexicon additions, edits and removals, admin logins, logouts and session revocations (an organisation admin's login says `via: oidc` and the profile's uuid), provider sign-ins (actor `profile:<uuid>`) and unbinds. Each entry holds who (`super-admin`, or `profile:<uuid>` for a room admin, with the name they acted as), the action, the target's kind, id and name at the time, details as JSON (4 KiB at most) and the time. An entry is written in the same transaction as its change: if the entry cannot be written, the change is rolled back and the request gets a 500. Deleting a room or a profile keeps the entries about it, with the old name. The server purges entries older than `GRILL_ROOM_AUDIT_RETENTION`, and expired sessions, at start and then daily. `/admin` shows the log read-only, newest first, filtered by action and by target id or name, each action in words and its details as key: value pairs.

The page is Preact, htm and @preact/signals, served from `internal/uivendor/esm/` like the daemon's page, and so is the room page's Room settings sheet. `make ui-check` runs `tsc --checkJs` on both.

## Rooms and invites

The admin token creates rooms and the first invites:

```sh
curl -H "Authorization: Bearer $ADMIN" --json '{"name":"Pricing review"}' localhost:7680/api/rooms
curl -H "Authorization: Bearer $ADMIN" -X POST localhost:7680/api/rooms/$ROOM/invites
```

The second call returns a `url` such as `https://<host>/join#<token>`. Whoever opens it picks a display name and lands in the room. One invite can be shared with several people.

Once in, each member has one shareable link per room, which "Invite people" shows; the server makes it on first use, and makes the room creator's with the room. Any member can create more invites and revoke the ones they created. The admin revokes any. Revoking an invite stops new joins through it; the people who joined through it keep their seats. A room admin or the admin can also tick "Also remove the N people who joined through it": that revokes the invites created by those who joined through it, and so on down the chain, so a member cut off cannot come back through an invite they made, removes those people, and posts who did it and who was removed. A revoked shareable link is replaced on the next ask. Before revoking, the page shows who the box would remove and who keeps access through another invite.

A room admin removes someone from People › ⋯ › Remove from room…, and may block their profile from rejoining; Room settings › Invites lists the blocks, with Unblock. A room admin steps down before anyone removes them. Anyone leaves from their own row's ⋯ › Leave room…. Their lines stay, marked "(removed)" or "(left)" until they come back, and the invites they made stop working.

A profile can also create a room from `/profile` ("New room"), within the limits set in `/admin`. It joins the room under the name it picks, through an invite of its own, and becomes the room's first room admin. A room admin opens "Room settings" from the room page's `⋯` menu, a wide sheet (full screen on a phone) with tabs: General (rename the room, copy its id, see its storage against its limit, delete it after typing its name), Invites (every invite, a new extra link, and revoke after a sheet that names who loses access), Admins (appoint other members as room admins or remove them, rename any participant), Personas, Skills, Plugins, Export and Words to recognise (the glossary). Each tab is a deep link, `#manage/invites`. A plain member's Room settings hold Invites (their own invites, a new extra link, revoke with the same sheet), Plugins, read only, and the glossary tab while an STT worker reads the glossary: with parakeet, none does, so that tab is hidden. The room keeps at least one room admin: the last one cannot step down. Room admin rights belong to profiles, so a member without one cannot be appointed. Each of these actions is a line in the chat and an audit log entry. The quota stays the admin's. A room the admin created has no room admin until the admin appoints one from `/admin`.

```sh
# Revoke an invite and remove everyone who joined through it: they get a 401 and their live stream closes.
curl -H "Authorization: Bearer $ADMIN" -X DELETE "localhost:7680/api/rooms/$ROOM/invites/$INVITE_ID?cut=1"
# Delete a room and everything stored for it.
curl -H "Authorization: Bearer $ADMIN" -X DELETE localhost:7680/api/rooms/$ROOM
```

A voice line joins its speaker's latest voice message when `gap_s` is under `GRILL_ROOM_VOICE_PARAGRAPH_GAP` and that message is still open. It is open while it is the room's latest message other than a typed one, comes from the same source, was neither edited nor deleted, has not been read by any agent turn, and the joined body stays within `GRILL_ROOM_VOICE_PARAGRAPH_MAX_CHARS`. A line without `gap_s` always starts a message. The append joins the bodies with one space and keeps the message's id and `ts`. It sets `appended_at`, bumps `change_seq` and writes no earlier version, so every page redraws the line through `message_edited` without an "edited" mark. The repeat check measures the 5 s from a paragraph's last append, and compares a line of 2 words or more with every run of the paragraph's words as long as the line, give or take one word. "Every N voice lines" counts a paragraph once it is closed: a message other than a typed one follows it, or `GRILL_ROOM_VOICE_PARAGRAPH_CLOSE` (20 s) passed since its last line. The server checks on each voice line, and, while paragraphs are on, on the 15 s trigger tick. A paragraph closed by that delay, a persona reply or a room event triggers within a tick, with someone here; a typed message closes none.

Request bodies must be JSON with `Content-Type: application/json` (415 otherwise), uploads excepted. A body over its route's limit gets a 413. Participants authenticate with `Authorization: Bearer <token>`, the room cookie set at join, the profile cookie, or a personal API token (API tokens, below). A browser's room cookie is tried first, then its profile cookie, which opens every room its profile has a participant in, as the newest of them. The server stores tokens as SHA-256 hashes.

## Profiles

The first join from a browser creates a profile and sets its cookie: HttpOnly, SameSite=Strict, valid for the whole site for 400 days. Every later join from that browser attaches the new participant to the same profile. `/profile` lists the profile's rooms, and the name in the room header links there. Its tabs are Rooms, Starters, Skills, API tokens and Account, each a deep link (`/profile#skills`); the line under your name always shows whether an email is on the profile.

After that first join, the room page's user menu (your initials) offers the profile's recovery link under "Use on another device", with a copy button. Without SMTP, a notice points there after the first message; with SMTP, a banner suggesting an email takes its place. The tab keeps it until "I saved it"; after that, the menu points to email sign-in instead. Opening it in another browser and confirming signs that browser into the profile, and from there into all its rooms. The page asks first, and warns when the browser already holds a profile: a link someone else sent would otherwise put the browser, and every room it joins next, in their profile. The link stays valid, so whoever holds it holds the profile. The server keeps only its hash.

With SMTP configured, `/profile` offers to bind an email. The server mails a link that binds the address once opened in the same browser. Opened in another browser, the page names the profile the address goes to and binds it only once you confirm; that browser keeps its own profile and nobody gets signed in. Later, "sign in with email" on `/profile` mails a sign-in link to a bound address, which signs a browser in after the same confirmation as a recovery link. Each link works once, for 15 minutes unless `GRILL_ROOM_MAGIC_LINK_TTL` says otherwise.

The join page offers "Recover my profile by email" while the browser holds no profile, and "Your profile" with its name once it does. A profile without an email shows a small silhouette next to its own avatar and name, to its owner only, and after its first message a banner suggests adding one; "Later" hides it for 14 days on every device. When someone has lost every device, the admin generates a one-time recovery link in `/admin` › Profiles: it works once, for 24 hours, and the audit log records both its creation and its use, never the link.

Someone with two profiles, say one per device, gets them merged by the admin in `/admin` › Profiles: pick the profile to keep (A) and the one to merge into it (B), read the preview, confirm. B's seats, personal and shared skills, templates, starters, created rooms, room admin roles and browser sessions move to A in one transaction, B's API tokens are revoked, and B is deleted, so B's devices are now signed into A. When the result is bound to the provider, the other side (B when A is bound to the configured provider, A when it takes B's binding, B also when both are) is signed out everywhere instead: browser sessions, seat tokens, push subscriptions, paired daemons and approved pairings (see Organisation sign-in). The sheet warns about it. A room where both had a seat keeps both seats, and every line its author. A personal skill whose name A already has gets `-2` (then `-3`, ...). The agent sees the new name, while the stored files keep the old one: to upload a new version of a renamed skill, set its SKILL.md frontmatter `name` to the new name, as an upload updates the skill its frontmatter names. A keeps its name, rooms limit and email; without one, it takes B's. A may end above a per-profile limit: it keeps everything and adds nothing more of that kind until under it. One audit entry holds both uuids and names and the counts moved, never an email. An export made before the merge carries B's uuid, which matches no profile after it.

A profile is empty when it is bound to no provider (spec 021), and has no email, no seat with a valid invite, no personal or published skill, template or starter, no room admin role and no unexpired API token. The server deletes empty profiles whose last activity (creation, join, message, sign-in) is over 24 h old, as `DELETE /api/profiles/{id}` would, at start and then hourly, at most 90 per run. A run that deletes writes one audit entry (actor `system`) with the count and the uuids. `/admin` › Instance turns it off. A browser whose profile was purged is signed out; its next join makes a new profile.

Within 15 minutes, a client IP may ask for 10 links, and for 3 to the same address; an address gets at most 10 whoever asks. That cap stops mail floods, at a cost: someone asking from 4 IPs can block an address's email sign-in for 15 minutes. The recovery link still works meanwhile. The client IP is the peer address. When the peer is in `GRILL_ROOM_TRUSTED_PROXIES`, it is the right-most `X-Forwarded-For` hop not in that list; a header from any other peer is ignored, so a client cannot spoof it. The admin login limit counts the same IP. A sign-in request gets the same answer, as fast, whether or not a profile holds the address: the lookup and the mail come after it. A bind request waits for the relay, so the page can say when the mail did not go out; after a bind send fails at the relay, sign-in requests answer "mail failed" for any address until a bind send succeeds or 5 minutes pass. Sign-in sends never move that state, as only a known address triggers one; a relay refusing one address does not move it either. Without SMTP, `/profile` shows no email option and the email routes answer 404.

The server uses STARTTLS whenever the relay offers it. A relay that offers none gets the links in clear, so keep it on a trusted network, as an in-cluster relay is.

### Organisation sign-in

With `GRILL_ROOM_OIDC_ISSUER` set, `/auth/login` signs a browser in with the provider.

- A profile bound to the account (`iss` + `sub`) is internal; any other profile, and a participant without one, is external.
- Only a binding to the configured issuer counts: after a change of provider, profiles bound to the former one are external; a sign-in with the new one opens a new profile, which the admin can merge.
- An external cannot create or import rooms, and invites only as a room admin of the room. The rule holds at join time too: an invite whose creator is now an external who is not a room admin stops working, even one made before the mode was on. An invite also stops working while its creator is an internal past `GRILL_ROOM_OIDC_REVALIDATE`, room admin or not, and works again after their next sign-in. The admin's invites always work.
- First sign-in: the unbound profile holding the account's email is bound to it, when the provider says the email is verified. That profile's other devices are signed out first, as it is now reached through the provider only: browser sessions, seat tokens (open room pages told at once, the seats leave the audio) and their push subscriptions, API tokens, paired daemons (their running turn fails) and the pairings its seats approved. Otherwise a new profile is created, with that email (if verified and on no other profile) and the account's name, cut to 40 characters.
- A profile the browser already held is never bound for being there. With an email, or bound to an account, it is left as is: the browser moves to the signed-in profile and its old session ends. The admin can merge the two.
- A guest profile the browser held at `/auth/login`, without an email and unbound, gets an offer once signed in, when it has rooms, skills, persona templates or starters: "Attach your guest profile <name> (<n> rooms) to <`GRILL_ROOM_OIDC_NAME`>, signed in as <account>?". <name> is "Guest" for a guest without one; <account> is the signed-in profile's name, else its email. Below it the page lists what would move: the rooms by name (five, then a count), and the counts of personal and published skills, persona templates and starters, so a guest someone else left on the browser shows as theirs. A guest with nothing to move gets no offer: its session ends, as above. The browser is already signed in. Attach merges the guest into the signed-in profile as the admin's merge does, audited `profile.merge` with the profile as actor and `"via": "oidc_attach"`; the guest's sessions, seat tokens, paired daemons and approved pairings end on every device, as for any merge into a bound profile. Not now leaves both apart and ends the guest's session on this browser. Either way the browser lands on `next`. The offer is never automatic, so on a shared browser the next person does not take the guest profile.
- The guest is sealed in the sign-in's state at `/auth/login`. The offer the page posts back is sealed on its own, bound to both profiles and to the guest's session on this browser, and expires with the sign-in, 10 minutes after `/auth/login`; that session expires with it, so an abandoned offer leaves no lasting session. The offer is refused, with "This offer expired. Your guest profile stays as it is; the admin can merge it into yours." and nothing merged, when it is expired, altered or answered already, posted from another site or by a browser outside the signed-in profile, or when the guest got an email, a binding, or was merged or deleted since.
- A merge keeps A's binding, or moves B's to A, without B's admin grant: A's next sign-in sets it. When the result is bound to the configured provider, the other side (B when A is bound to the configured provider, A when it takes B's binding, B also when both are) is signed out everywhere instead of moving or keeping its sign-ins: its browser sessions, its seat tokens (open room pages are told at once, the seats leave the audio) and their push subscriptions, its paired daemons (their running turn fails, as when the host removes the room), the pairings its seats approved and its API tokens; B's API tokens go with any merge. Another device holding them would act as the result without the provider. Those devices sign in through the provider, or come back through an invite; a daemon pairs again. A binding to a former issuer, or restricted mode off, counts as none: the merge moves everything as above. When both are bound, B's binding is dropped with B; the merge's audit entry says `dropped_oidc_subject`. B's provider admin sessions end with B.
- Each sign-in writes a `profile.oidc_bind` audit entry with `how`: `existing`, `email` or `new`.
- Each sign-in in flight has its own cookie (state, nonce, PKCE verifier): HttpOnly, SameSite=Lax, scoped to `/auth`, 10 minutes; a new sign-in keeps the 4 newest and clears older ones. `next` is kept up to 512 bytes.
- The client is confidential: `GRILL_ROOM_OIDC_CLIENT_SECRET` is required.
- Groups are read from the ID token: configure the provider to put them there, as names, not ids; some providers need `groups` in `GRILL_ROOM_OIDC_SCOPES`.
- Email binding needs the boolean claim `email_verified: true`, or Entra's `xms_edov: true` (add the `email` and `xms_edov` optional claims to the ID token); a string `"true"` does not count. A bound profile without an email gets the verified one at its next sign-in, when no profile holds it; it never replaces its own.
- An internal's sign-in lasts `GRILL_ROOM_OIDC_REVALIDATE` from its last one. Past it, its profile cookie, its room seats and its API tokens answer 401 `reason: reauth` on every route, its open room page streams end with `revoked` `{"reason":"reauth"}` within a heartbeat, and its seats leave the audio. The seats' paired daemons get 403 `reason: reauth` and keep their pairing: their stream closes without `revoked`, they retry more slowly until the owner signs in again, and they may still remove themselves; nothing is deleted, and a new sign-in restores them. A page answered `reauth` goes to `/auth/login?prompt=none` and comes back where it was; its fragment waits in the tab, never in the URL. A browser signed in since as another account gets 401 "invalid or revoked token" for the former account's room cookie, which is cleared.
- An internal never signs in by email or recovery link, the admin's one-time ones included: the link page says so and links to `/auth/login`; no sign-in link is mailed to it, with the same answer as for any address. Externals keep both.
- The join page shows "Sign in with <`GRILL_ROOM_OIDC_NAME`>" above the name form, until the browser is internal. The sign-in comes back to the invite, its fragment kept in the tab, and the join then joins as internal. Without an invite the page shows only that button.
- Groups are read only at sign-in: an internal whose last sign-in held `GRILL_ROOM_OIDC_ADMIN_GROUP` opens `/admin` without the token. The grant keeps the group's name. Its admin sessions end, at their next request, when the profile's sign-in expires, when a sign-in no longer holds the group (removed at the provider), when `GRILL_ROOM_OIDC_ADMIN_GROUP` changes or is unset, when the issuer changes, when the profile is unbound or deleted, and when a merge deletes it as B. A bound profile is never empty, so the purge of empty profiles never ends them. With restricted mode turned off, they are refused, and kept for when it comes back. Admin-token sessions are not affected.
- `/admin` › Profiles shows each profile internal or external, its last sign-in, and "sign-in expired" past the revalidation. Its ⋯ menu unbinds a bound profile: it becomes external, and its next sign-in with the provider finds it again by verified email only, as any unbound profile. Unbinding turns the person into a guest and signs the person out everywhere: browsers, API tokens, room seats and their Web Push subscriptions, paired daemons; they come back as a guest through their recovery link or an invite; delete the profile to keep them out. Their provider admin sessions end too; their seats stay, with their messages, and come back with the profile.

### API tokens

`/profile` › API tokens makes personal tokens for scripts and AI agents: a name, an expiry (30 days, 90 by default, a year, or never) and a scope, read only or full. The token, `grt_` and 26 base32 characters, shows once; the server keeps its SHA-256 hash. Send it as `Authorization: Bearer grt_…`:

```sh
curl -H "Authorization: Bearer $TOKEN" https://<host>/api/profile
```

A token acts as its profile: on a room route as the profile's newest participant there, with that participant's rights (member, room admin, AI host); a room the profile is not in answers 403. A read-only token gets 403 on any method but GET and HEAD. A token never reaches `/api/admin/*` or any route behind the admin check, whatever its scope (403), and never makes another lasting credential: the token routes, join, email bind and sign-in, recovery, pairing and Web Push answer it 403. Invites are the one exception: an invite link made with a token, the shareable one included, outlives the token. An expired token answers 401 "This token has expired" and stays listed for 30 days, then the daily purge deletes it; a revoked one answers 401 at once. Each use records its time and client IP, at most once a minute; the purge clears the IP after `GRILL_ROOM_CLIENT_RETENTION`. A profile holds at most 100 unexpired tokens. Creating and revoking a token are audited, and an audited action done with a token names its id. `GRILL_ROOM_ADMIN_TOKEN` may not start with `grt_`.

### Agent access (MCP)

The room server speaks MCP at `/mcp` (Streamable HTTP, JSON answers, no session), with the same token. The new-token sheet shows the line to paste:

```sh
claude mcp add --transport http grill-room https://<host>/mcp --header "Authorization: Bearer grt_…"
```

Its 27 tools read your rooms (`list_rooms`, `get_room`, `list_documents`, `read_document`, `get_transcript`, `list_notes`, `list_invites`, `list_starters`, `get_starter`, `list_templates`, `list_skills`, `list_plugins`) and set them up (`create_room`, `add_persona`, `edit_persona`, `set_persona_skill`, `set_persona_plugin`, `add_room_skill`, `check_plugin`, `add_plugin`, `save_room_as_starter`, `upload_document`, `get_invite_link`, `delete_room`, `delete_document`, `remove_persona`, `revoke_invite`). A read-only token lists the read tools only. Each tool calls the REST routes it names, with your token, so a tool can do exactly what the route lets you do; a refusal comes back as a tool error with the route's message. The host's approvals apply as in the room, and no tool approves, posts a message or runs a persona. The four destructive tools need `confirm` equal to the target's exact name (an invite's id for `revoke_invite`) and are audited with the token's id. `/mcp` answers 401 with no OAuth metadata to anything but an API token, 405 to GET and DELETE, and 403 to a foreign `Origin`. `grill_room_mcp_tool_calls_total{tool,result}` counts the calls on `/metrics`.

- Access is by invite link. Anyone holding a valid one can read the room, and any member can make more.
- Tokens are stored as hashes, except each member's shareable link, kept as is so "Invite people" can show it again: the database holds one working shareable link per member and room in clear. Exports never carry it.
- No audio is stored. Rooms and profiles live until deleted, except empty profiles, purged after 24 h of inactivity (see Profiles).
- Deleting a room removes everything stored for it. A profile outlives its rooms and stops listing them.
- Deleting a profile (`DELETE /api/profiles/{id}`) removes its sessions, its pending and used links, its email, the persona templates it published and its personal skills. Shared skills it published stay in the library under the display name that signed them. Its participants stay in their rooms under their display names, detached from it. Every browser signed into it is signed out.
- A delete removes the rows from the tables at once. Their bytes stay in the database files until PostgreSQL's autovacuum, or a `VACUUM`, reuses the space, and in backups until their retention ends. The server runs no `VACUUM` of its own.
- Logs carry profile ids, never emails.

## Export and import

A room admin, from the room page's Room settings, or the admin, from `/admin`, exports a room as a `.tar.gz`: the room's settings and personas, every line with its earlier versions and deletions plus a readable `transcript.md`, documents with all their revisions, uploads (originals and their Markdown copies), annotation threads with their images, the room's skills and the shared and personal skill versions its personas pin, the room's plugins with their versions and snapshots (see Room plugins), the agent sessions, and the participants as display name and profile uuid. No email, token or invite leaves. `manifest.json` lists every file with its sha256, the format version and the exporting instance's version. docs/export-format.md describes the files.

The agent sessions hold everything Claude read in the room. The export panel says so, and so does the import preview.

`/admin` imports an archive, as does a profile allowed to create rooms through the API. The import first shows a preview: room name, counts per kind, sizes, the format and the exporting version, and warnings. Nothing exists until the admin confirms; the preview runs the whole import and rolls it back. The import makes a new room with new ids:

- Participants whose profile uuid matches a profile here are relinked to it, and a relinked room admin stays one. The others keep their uuid as `profile_uuid_hint`, unlinked. A profile importing relinks itself, and the other participants only if it administers the exported room on this instance: an archive cannot seat anyone in a room its importer controls. The importing profile becomes room admin, and gets a seat under `display_name` unless it is among the participants.
- No old invite or token opens the new room: they are not in the archive.
- Each persona resumes its agent session from where its last turn left it.
- On the instance that exported it, the pinned shared and personal skills link back to the library when it still holds the same versions. Elsewhere they become room skills, renamed `<name>-2` if the room has one of that name.
- Plugins land pinned at their exported versions, each waiting for this instance's AI host to check and approve it.
- Personas waiting for the host's approval, held persona changes, requests to the AI host to fetch a plugin and the turn history are not exported.

An import is refused, with the reason and with nothing created, for a file whose sha256 differs from the manifest, a format newer than the instance reads, a path that is absolute or holds `..`, an entry that is not a regular file (symlink, hard link, device, FIFO, directory), more than 50 000 files or more than `GRILL_ROOM_MAX_IMPORT_MB` uncompressed, an upload or image whose content is not what the room accepts, a plugin snapshot a daemon's upload would fail (not a normalised snapshot, over the instance's plugin size limit, or not matching its sha256), a plugin link with credentials, or a room too large for this instance. "Too large" counts two things. The room quota counts the uploads, annotation images and plugin snapshots, as for a live room, against the instance's default room quota. The instance storage quota, when set, counts the whole uncompressed archive against what the database has left.

Exports and imports stage their files in `GRILL_ROOM_STAGING_DIR`, removed after the request and at the next start, so its filesystem needs room for the archive. The server refuses to start if that directory is a symlink or belongs to another user. At most two run at once; a third gets a 503, and each one gets 30 minutes to upload or download. An export reads the room from one snapshot and blocks no one. An import holds the server's write lock while it writes the room, so other writes wait: seconds for a room at its quota, more for long agent sessions, which no quota bounds. It renders its lines before it takes the lock.

## Documents

Any participant can add Markdown, HTML, PDF, PNG, JPEG, GIF, WebP, SVG, DOCX, ODT or PPTX, several at once: the Documents header's `+` button, or a drop on the documents list (anywhere in the docs window). Each file shows its progress, then ✓, or ✗ with the reason and Retry; a done row clears after 5 s. The page refuses an unlisted extension before sending it. The server reads the content to decide the type. The extension only picks between text formats, so a binary file named `.md` gets a 415. Uploads are read-only. The room keeps the original, and pandoc turns DOCX, ODT and PPTX into a Markdown copy that the room shows. Documents the agent writes take revisions instead.

Markdown renders GitHub-style: tables, highlighted code, mermaid diagrams, math, alerts, footnotes. Every rendered document, uploaded HTML included, loads in an iframe sandboxed without `allow-same-origin`, and its response carries a `sandbox` CSP. A script in it runs in an opaque origin: it cannot read the room cookie, and the CSP blocks fetch, XHR and form posts.

Any participant renames a document from the viewer's `⋯` menu, which also holds Download (uploads) and Open in a new window: it keeps its id, revisions, annotations and links, the chat says "Alice renamed `a.md` → `b.md`", and a persona resuming its session reads the old and new workspace paths in its next turn's prompt. A room admin deletes one from the viewer, softly and at once, with Undo in a toast for 5 s: it leaves the list, the workspace and what the agents read, but its data stays, counts in the room's volume and goes only with the room. Room settings, Documents tab, restores it, unless another document took its name. An agent document is neither renamed nor deleted while a turn runs, as the turn would write it back under the name it read. Exports carry deleted documents, flagged.

The Documents header's external-link button, or `⋯` › "Open documents in a new window", puts the document manager in a window of its own, `/r/<room>/docs`: the list, uploads, the viewer, annotations, revisions and diffs, kept live by the room's event stream like the room page. Its address follows the document shown, so `/r/<room>/docs/<doc>` opens that document. A second click reuses the same window, and the room's name in its header leads back to the room.

From 64rem up, the documents list (the side panel on the room page) and Notes keep the width you drag their edge to, also with ← and →; the document keeps at least 24rem in the docs window and with the chat folded. Above 40rem, each drawer of the side panel folds on its own, Documents and People, with the triangle at the start of its header or a click on the header, and the panel narrows to a rail once all of them are folded. Markdown reads at Narrow, Large or Full width (the ↔ button). Voice lines run in a Transcription pane from 64rem up, right of the chat while it keeps 22rem beside it (once hidden, it comes back with 1rem more; 320 px wide by default, its left edge dragged between 192 and 480 px), or above the chat while a document is open. On a narrower screen, beside a wide side panel or with the pane folded, they stay in the chat behind its All · Written · Voice filter, Written by default; sending a typed line under Voice, or a link to a line the filter hides, shows All for that visit without changing the choice. When the pane opens or closes, a line holding focus (its edit box, its menu button or a link in it) stays in view, and shows All for the visit if the filter would hide it. These choices stay in the browser, for every room. On a phone the docs view shows one pane at a time, the list, the document, then Notes, and Back steps through them.

The Docker image ships pandoc's official static build. The image grew from 16 MB to 174 MB, 147 MB of it pandoc (7 MB to 49 MB gzipped). Math renders with fallback glyphs for now: MathJax fetches its fonts from a CDN, and the CSP blocks that.

## Annotations

Select text in a Markdown or HTML document, or in the Markdown copy of an office file, and press Annotate. In an HTML document, "Annotate an element" picks an element instead. "Comment on the document" works on every document, PDF and images included. Each annotation holds a thread. Every message can carry up to 4 PNG, JPEG, GIF or WebP images; the server reads the type from the bytes and refuses SVG. Anyone can mark a thread done, and a participant's reply reopens it.

A text anchor is a quote with 32 characters of context on each side, matched the way grip-live-diff does. An element anchor is an `nth-of-type` path from `body` plus the first 80 characters of the element's text. When a script rebuilds the page, the mark moves to the element whose text matches. When the agent writes a new revision, the server re-anchors every annotation on it. A reworded quote follows its context. An annotation whose text or element is gone is flagged orphaned and stays in the list with the revision it was last seen in.

The document frame has no room credential, so it cannot call the API. It tells the room page what was selected or clicked through `postMessage`. The room page drops any message that is not from the frame on show, not from an opaque origin, or not of the expected shape and size. A participant still has to type and save the comment. The frame receives anchors and statuses only, never thread text or names.

`store.AnnotationsSince` is the read for the agent's turn: every thread with a message past a cursor, with its image bytes.

An `@name` in a note calls a persona as in the chat: same rights, same notices for its author, and a "→ @Persona" chip on the note message that follows the turn. A thread whose participants named personas belongs to them. Another persona's prompt leaves it out of the new threads, and its reply or close there is refused and listed in its turn's report. A persona naming another in its own reply claims nothing.

One persona per room may watch the notes ("Watches the notes", in its sheet's Triggers tab). It answers the threads that name no persona once `GRILL_ROOM_NOTES_WATCH_DELAY` (20 s) passes with no new note message; each new message restarts the wait. Its own messages and notes never wake it, another persona's do. Its turns are chain links, like every N answers, with one difference: at the limit it waits quietly, with no line in the chat, and runs once the limit lifts. The persona row, its pill and the Notes pane show who watches.

## Voice

With `GRILL_ROOM_LIVEKIT_URL` set, the room page shows a Join audio button; once joined, a row of icon buttons, each with its tip below it: my mic, mute the room, transcribe my voice, ⋯ (the rarer options) and leave audio. Each grill room maps to one LiveKit room named after the room id. A participant joins it under their participant id with their display name, and may publish their microphone only. "Mute the room" (deafen) stops hearing the others and mutes the mic, unless "Keep my mic on while the room is muted" is checked in ⋯, for people who share a physical room; pressing it again restores the mic as it was. "Transcribe my voice", on by default, turned off keeps that participant's voice out of the transcript, the server's and their device's, until they turn it back on, across reloads and audio rejoins; the others see it as their "transcribed" badge going away. The state outlives a reconnect within the browser session.

On-device transcription (spec 010) needs the model files: `grill-room models fetch --dir <dir>` downloads the manifest pinned in the binary (about 430 MB), skips files already there with the right sha256, and exits non-zero on a mismatch. With `--best-effort`, as the Kubernetes init container runs it, a failure logs one line and exits 0, and the server then offers no device mode. With `GRILL_ROOM_DEVICE_STT_MODEL_DIR` pointing there, `GET /models/<revision>/<file>` serves those files, cached as immutable, and the `stt` event carries a `device` object with the revision, total size and each file's integrity hash.

## Presence

The participant list shows "In the room", then "Not here", collapsed, with when each was last seen. On a phone the 👥 button opens it as a sheet over the chat, closed by its ✕, a tap outside, Escape or picking a document. The server keeps presence from each page's event stream and a heartbeat every 10 seconds: a participant stays here while one of their pages holds its stream open, and for 20 seconds after their last sign of life, so a reload, a background tab or a phone switching apps does not flap. A closing page says so, and the audio state it held goes at once. Each page reports its audio state, and every participant sees it, in the audio or not: mic live, muted, listening only, or not in the audio, with an icon when deafened. Icon badges, each with its meaning in a tip on hover, mark you, the AI host (whose computer runs the personas) and room admins, who can ask the AI, and each voice the STT worker hears ("transcribed"). Those in the audio also see the speaking dot, and a volume control per remote participant in their `⋯` menu.

Each person is one row: a status dot, the name, then badges in aligned columns (you, AI host, admin, can ask the AI, transcribed, audio), each with its meaning in a tip on hover. Settings about a person sit in their `⋯` menu, not in the row: a room admin renames them and makes them a room admin or removes it, the AI host lets them ask the AI, the AI host or a room admin makes them the AI host when their AI host app is connected, and anyone in the audio sets their volume. A room admin who takes the role from someone else confirms first; the previous host's page then says who did it and that their app stays connected as a standby. The super-admin does the same from the room's Admins tab in `/admin`.

Hovering a name in People or on a chat line for 300 ms, or focusing it, shows a details card; on a phone a tap on the row opens it. It lists the name and the one before the latest rename, the roles (you, room admin, AI host, standby host when their app is connected but not hosting), "Can ask the AI", the audio state, whether the transcription hears them, here since or last seen, and when they joined. Escape closes it. It shows no IP address or user agent: those stay in `/admin`.

A participant changes their own name from the user menu, "Change my name", with the same rules as at join, and may make it their profile's name too. A room admin, from Room settings, or the admin, from `/admin`, renames anyone, and the renamed person sees a notice. The chat says who renamed whom. Earlier lines show the new name, with the one they were written under on hover. The agents' presence preamble keeps the same short id after the name, as it comes from the profile.

A participant turns on browser notifications for a room under Notifications. A sheet says what they are for before the browser asks for permission, and the room offers it once on its own, after the participant's first line in a page load; "Not now" keeps it quiet for 14 days in that browser, in every room. They come through Web Push, so they reach a background tab and a closed browser, but only while none of that participant's tabs in the room is focused: each page tells the server when it gains or loses the focus. By default a notification comes for a mention of the participant, in a line or a synthesis, a persona's synthesis, and the end of a turn they started; "Also every other line" adds the rest. Events of the same room within 5 seconds make one push, and the phone shows one notification per room, counting the events. Clicking it opens the room's chat scrolled to the line that triggered it, `/r/<room>#m<line id>`, in the room's open tab if there is one. The payload holds the room's name, the kind of event and a link, never a line's text: it passes through the browser vendor's push service. The VAPID key pair is generated on first use and kept in the database; a room page holding a subscription made with another key, as after the key changed, deletes it and subscribes again, for every room turned on in that browser. When the browser renews a subscription on its own, the service worker hands the new one to the server for every room turned on in that browser. A subscription the push service reports gone (404, 410) or refuses (a 403, or a 401 for another VAPID key) is dropped; any other 401, or a 403 naming the JWT as Safari's push service sends, points at the server's own VAPID setup, so the subscription stays and the server logs `push_unauthorized` as an error. Subscriptions also go with their participant and their room. On iPhone and iPad notifications need the room added to the home screen; the page says so, and the web manifest opens it standalone for that.

In the chat, `@Grill` shows as a chip in the persona's colour with its badge, and `@Ana_María` as a chip for that participant; an `@name` that names nobody in the room stays text. The server decides what a line names, by the same rule that calls personas, and sends it with each line (`named`); the page only draws it. A line that names you is highlighted, with an accent bar. A copy of the line still reads `@Grill`.

While the room's tab is not focused, its title counts new lines from others and syntheses, "(3) Pricing review · grill-room", and resets once the tab is focused again. "(4 @)" says one of them names you. Voice lines count only when "Count voice lines in the tab title" is ticked, under Notifications.

The server hands out LiveKit tokens valid for 5 minutes, and LiveKit refreshes them for connected clients. LiveKit has no way to revoke a token. So when someone loses their seat, the server also removes them from the LiveKit room, and deleting a room closes its LiveKit room. A revoked participant could still rejoin with a token minted before the revoke, until it expires.

Media needs no published UDP port (spike S4): ICE runs over TCP 7881, or TURN over TLS on 443, where traefik terminates TLS and routes `turn.<dev-domain>` by SNI to LiveKit's plain TURN port.

While an STT worker is in its audio, the audio menu counts the voices it transcribes, "2 voices are being written down": the participants whose track a worker is subscribed to. A participant whose own voice is one of them also reads "yours is one of them", and their transcription button carries a dot; one who left the audio, or never joined it, reads nothing about their own. "Voice-to-text is off" shows in the audio menu, so only to people in the audio, when no worker has sent a heartbeat for 15 s. Audio and text keep working meanwhile.

Each room has a transcription glossary: terms people will say, one per line or comma-separated, 60 characters each, 2000 in all. Any member edits it in Room settings, and the room shows who changed it. The default engine, parakeet, has no input for it, so Room settings hide the tab while no worker reads the glossary; the glossaries stay stored, exported and imported. S10 and S10d found parakeet-ultra writes French with English jargon right without a list, and Claude reads the transcript afterwards anyway. With `APP_ENGINE=whisper` and `APP_GLOSSARY_PROMPT=on`, before each utterance, the worker reads the room's prompt (`GET /api/stt/rooms/{room}/prompt`, with its service token) and passes it to faster-whisper as `initial_prompt`, never as `hotwords` (spike S10). It is off by default: on real speech the prompt made `small` worse, as it loops on the prompt and drops text (spike S10b). The glossary is kept for an engine that takes a word list. The prompt is one French sentence: the glossary, then the participants' and personas' names, then the documents' titles, taken in that order while an estimate stays under Whisper's limit of 223 tokens. Room settings show how many terms fit, "12 / ~70 terms used". The sentence puts the glossary last, so if Whisper cuts an overlong prompt from its start, the titles go first.

### STT worker

`stt/` is a Python service. It polls LiveKit for rooms with participants and joins each one as a hidden participant that cannot publish. Then it listens to every participant's audio track, and closes that listener when the track is unsubscribed or unpublished, when its participant leaves, or when the worker leaves the room. LiveKit reuses a freed transceiver for the next track it sends the worker, so a listener left open would hear the newcomer and post them under the old name (spike S5). Silero VAD cuts each track into utterances after 800 ms of silence, or at 15 s. parakeet-ultra then transcribes them through transcribe.cpp, Q8_0, greedy, with no language argument: it writes French and English as spoken (spec 007, spike S10d). On the lab's real French speech it had a WER of 0.232 on meetings and 0.121 on a talk, against 0.326 and 0.257 for faster-whisper `small`, at half the latency.

`APP_ENGINE=whisper` brings back faster-whisper `small` int8 for one release, the rollback path. It detects the language per utterance, so French and English mix freely (spike S1-bis). Detection and decoding share one encoder pass: faster-whisper's own `transcribe(language=None)` runs two and throws the first away, which doubled the cost per line. Each line goes to `/voice/lines` under the speaker's participant id. The worker sends a heartbeat every 2 s, and at once when it joins or leaves a room or a track or when the server flags or clears a participant transcribed on their device. It keeps its subscription to a flagged track and drops its audio before the VAD.

Before posting, the worker drops a transcript that fails one of these checks, and counts it in `grill_stt_lines_implausible_total{reason}`. Each threshold is a setting, in brackets. Parakeet gives no confidence and no language, so with it only `repetition`, computed on the text, and `script`, against Latin letters, apply. Parakeet turns a TTS glitch into Latin-letter babble that no check catches (`stt/tests/fixtures/voices.json`).

| Reason | Dropped when |
|---|---|
| `avg_logprob` | the lowest segment's mean token log-probability is under -1.0 (`APP_MIN_AVG_LOGPROB`), Whisper's own failure threshold |
| `repetition` | a segment's gzip ratio is over 2.4 (`APP_MAX_COMPRESSION_RATIO`), Whisper's sign of a looping decoder |
| `no_speech` | a segment's no-speech probability is over 0.6 (`APP_MAX_NO_SPEECH_PROB`) and the language is unsure. Whisper itself keeps a likely-silent segment it decoded confidently |
| `language_probability` | the language is detected at under 0.5 (`APP_MIN_LANGUAGE_PROBABILITY`) on an utterance of 2 s or more (`APP_SHORT_UTTERANCE_S`). Shorter ones pass: Whisper often hears a French "oui" as English at 0.3 |
| `script` | under 90% of the letters (`APP_MIN_SCRIPT_SHARE`) are in the script of the detected language, like Chinese characters for `fr` |

Audio stays in memory. Samples go from the LiveKit stream to the VAD, then to a bounded queue, then to an engine process over a pipe, and are released once transcribed. Nothing is written to disk. The worker runs `APP_ENGINE_PROCESSES` engine processes; each takes the oldest queued utterance whose speaker has none in an engine, so a speaker's lines post in order while other speakers pass. A process that dies, or hangs past `APP_ENGINE_TIMEOUT_S`, loses its utterance and is restarted. When the queue is full, a new utterance is dropped, counted, and announced in the room, "Transcription overloaded: one line lost for <name>.", once per speaker per 30 s. [docs/architecture.md](docs/architecture.md) has the capacity, the metrics and the alert. The worker logs the size of each line and a language guess, `fr`, `en` or `unknown`, from a count of function words, never its words. The guess also feeds `grill_stt_lines_language_total{engine,guess}`: English lines in a French room show an English leak. It never reaches the room server.

The image bakes both models in and runs with `HF_HUB_OFFLINE=1`, because a pod behind a default-deny egress policy could not fetch them at start. Whisper comes at a pinned Hugging Face revision. The parakeet GGUF comes from `handy-computer/parakeet-ultra-gguf` at a pinned revision, and the build fails if its sha256 differs. transcribe.cpp is compiled in the image from a commit pinned by full SHA, for the AVX2 baseline, never `GGML_NATIVE`: an image built on a newer CPU must run on the lab's AVX2 nodes. The worker loads it through its ctypes binding and `TRANSCRIBE_LIBRARY`. Compose gives it 4 CPUs and 3 GiB: two engine processes of 2 threads and 1.2 GB each (spike S10d).

| `APP_VAD_CUT_SEARCH_S` | `3` | how far back from that limit a forced cut looks for the quietest moment, so it does not land mid-word; `0` cuts at the limit. Must be 0 or more and below `APP_VAD_MAX_SPEECH_S`, or the worker does not start |
| `APP_POLL_SECONDS`, `APP_HEARTBEAT_SECONDS` | `2`, `2` | room discovery and heartbeat periods |
| `APP_PORT` | `9100` | `/healthz` (503 while the models load, and once no engine process has been up for 60 s) and `/metrics` |
| `APP_WORKER_NAME` | hostname | name in heartbeats; LiveKit identity `stt-<name>` |
| `APP_LOG_LEVEL` | `info` | |

Metrics: those in [docs/architecture.md](docs/architecture.md), plus `grill_stt_rooms`, `grill_stt_tracks` and `grill_stt_device_tracks` (tracks skipped because a device transcribes them, or their participant turned their transcription off).

`python -m grill_stt.replay` plays WAV tracks in real time, one or several speakers at once, through the worker's own segmenter, engine processes and filter, and writes each line with its latency: the lab A/B run of spec 007 (`spikes/s007-ab/`) uses it in the image.

`make stt-image-test` runs the worker's e2e tests inside the built image with no network, for both engines: each must load its baked-in model offline.

The voice e2e tests play `e2e/voice/fixtures/fr-en.wav` as a fake microphone. It holds four read sentences from Google FLEURS (CC-BY-4.0), alternating French and English. `fr-en.json` gives their source files, text and timings. `uv run ./scripts/make_fixture.py ../e2e/voice/fixtures` (from `stt/`) rebuilds them.

## Agent

The agent runs on a participant's machine, through their host daemon (below). The first participant whose daemon connects and can host becomes the host. When the host's daemon drops or can no longer host, the room moves the role to the daemon that connected earliest among those that can. The host can hand the role to anyone whose daemon is connected. Each persona's LED in the header is green while the host's daemon is connected, amber during its turn, blue while it waits in the queue, and red with the reason when no host can run the agents. Transcripts keep recording either way.

A room holds personas: agents with a name, a badge, a colour, a text that sets their role, and the model and effort they ask for. Every persona names both; there is no "default" that only the host could read. Personas and templates from before that ask for `sonnet` and effort `medium`. Every room starts with Grill, from the Grill template, which challenges the plan. The Secretary template takes notes. The Rodin template asks whether an idea should exist at all, before anyone grills the details; the Spec grill starter has it too. In the Personas sheet (`⋯` › Personas) any member adds a persona from the template library. Each persona is one row there: badge, name, model and effort, trigger and state. A row opens that persona's sheet, with an Identity, Model, Triggers and Capabilities tab (each a link, `#personas/<id>/<tab>`), one Save for all four, and Remove in its `⋯` menu. A right-click or a long press on a persona's pill opens the same sheet. Each change is a line in the chat and applies from that persona's next turn. A template's newer version is offered to the room, never applied by itself. A profile can publish a persona as a template, and new versions of its own templates.

Each persona has its own button. The host can press them and can let other participants press too, with "Can ask the AI" in their `⋯` menu in People. A pill someone may not press still opens, to say why and who can change it. One press runs one turn of that persona: it reads what was said and annotated since its own last successful turn, other personas' syntheses included, edits or writes documents, answers threads and may close them, opens annotations of its own on any document, uploads included, and posts a synthesis. The synthesis shows the persona's badge and name and the model and effort the turn ran with. A new agent document never takes an upload's name. One turn runs at a time in a room: a press during a turn waits in a queue shown under the header, which the person who pressed can cancel. A turn the room handed over can still wait on the host's machine, behind turns of the host's other rooms: its LED stays blue and the header says "waiting (the AI host is busy)".

The host can tick "Personas answer at the same time" in the Personas sheet. Two personas then run at once, each in its own sandbox; a press waits only while that persona runs or waits already. A turn's workspace holds each agent document at the revision it had when the daemon first fetched it. When a turn writes a document another turn revised since, its whole result is set aside and the turn runs again, ahead of the queue, on the new version; the chat says so, and the re-run is no chain link. If the re-run conflicts too, the turn fails with "conflict on <document>". Replies, new annotations, syntheses and new documents never conflict. The server counts both outcomes in `grill_room_turn_conflicts_total{outcome}`. "Start fresh" (host only, in the persona sheet's `⋯` menu) starts a persona without its memory. It then rereads the room history from the transcript files. "Start fresh, keep a summary" (host only) first runs a last turn that writes `docs/_handoff-<persona>.md`, then starts a new session told to read that note and the transcripts; if the last turn fails, the persona keeps its session. The persona sheet's Model tab shows how much of its context window the persona's session holds, and above 80% the room offers the host that handoff. "Memory size", on the same tab, sets the autocompact context size, in thousands of tokens from 100 to 1000, at which Claude Code compacts the persona's session; empty leaves it to Claude Code. The room keeps each persona's Claude session after every turn, so when another daemon takes over, each persona's next turn resumes its own session. [docs/agent-workspace.md](docs/agent-workspace.md) has the details.

### Skills

A skill is a Claude Code skill folder: a `SKILL.md` whose YAML frontmatter has a `name` (lowercase letters, digits and hyphens) and a `description`, plus any files it needs, scripts included. The profile page uploads one as a zip, with `SKILL.md` at the root of the zip or of its single folder. The upload is personal, kept in the profile and offered only in rooms that profile is in, or shared, in the library every room sees. Uploading a name again publishes its next version; versions never change. The server refuses a zip with symlinks, absolute or `..` paths, more than 200 files, or more than 8 MB packed or unpacked, and says why. The admin can remove any skill. Skills never come from the host's disk.

A member can also copy one of their personal skills into the room from the Personas sheet (`⋯` › Personas). The copy is the room's: frozen at the version copied, offered to every member, and kept when its author leaves the room or deletes the original, unlike a personal skill, which rides only while its owner is a member. The copy is a line in the chat. While the host approves everything, it waits for the host before any persona can use it. A room admin removes room skills from Room settings; deleting the room deletes them.

On a persona sheet's Capabilities tab any member with a profile turns a skill on for that persona, from the shared library, their own personal skills or the room's skills, and anyone turns one off. Each change is a persona change: a line in the chat, held while the host approves everything. The persona keeps the version it was turned on at. A newer upload shows as "Update to vN", applied only when someone takes it. The first time a profile turns any skill on, the sheet shows a disclaimer once:

- a skill's scripts run in the host's sandbox, on the host's machine;
- anyone in the room can ask the agent to print a skill's content, so a skill must hold no secret;
- the sandbox reaches the Internet only through the host's egress allowlist, which does not inspect traffic, so a script can send room data to any allowed domain that accepts uploads, GitHub included when the script carries a token.

The turn hands the skills to `claude -p` as a plugin directory with `--plugin-dir`. [docs/agent-workspace.md](docs/agent-workspace.md) has the layout.

### Room plugins

A room admin adds Claude Code plugins from Room settings › Plugins: "Add a plugin" takes a repository link and a git ref (empty for the default branch), and Check lists what the repo holds. A marketplace lists its plugins, none checked, and the ones stored elsewhere are greyed out with the reason. The admin also picks the personas to turn it on for, none checked by default. The list shows each plugin as "rich, main @ 3c23934", the version in use, and where a newer one stands. Its `⋯` holds Update, which says "Up to date" or adds a version, and Remove. Every member reads the list; only room admins see these actions.

A new version waits for the AI host's app to check it. While the host approves everything, it then waits for the host: the status strip and the plugin's row offer Review, which opens the approval sheet. That sheet shows the repo, ref, commit, size, the components with their names, each hook's command and each MCP or LSP server's command or URL highlighted, the websites MCP servers name, what grill-room could not read, Claude Code's warnings and the token cost per answer. For an update it adds the change against the version in use: components and files added, removed and changed, and a compare link on GitHub and GitLab, both commits elsewhere. A persona's Capabilities tab lists the room's plugins: a room admin turns each on or off there. Each row gives the version, its token cost or why it does not load, and the tab totals the cost of those that load.

The server fetches public https repos only. When it cannot read one, because the repo asks for a login, is not found, or is an ssh link (`git@host:owner/repo`), the add form offers "Ask the AI host to fetch it", with an optional list of plugin names for a marketplace repo and the personas to turn them on for. The request waits in Room settings › Plugins. The host's daemon page lists it on the Rooms tab with who asked, the link and the ref, and nothing is fetched until the host presses Fetch, whatever the approval mode: the fetch runs the host's own git, with their ssh keys, `gh` login and credential helpers, outside every sandbox. Git runs with no prompt and no askpass program, https and ssh only, no submodule, no hook and no LFS download, within the 60 s and size limits of a server fetch; at the deadline the daemon kills git and what it started (git only on Windows). The daemon reads the commit's files without a checkout, builds the snapshots and uploads them; the server checks them again and marks the plugin private. Update on a private plugin makes the same request. A host whose git cannot reach the repo answers "This AI host cannot reach the repo", and the version in use keeps running.

A plugin may declare options (`userConfig`). The host sets them on the daemon page, per room: the Rooms tab shows a form per plugin, each option with its title, description and type. A sensitive option is a password field, and its value is never shown again, only whether it is set. The form warns: "The AI can read these values during a turn. Anyone in the room can ask it to show them." The values stay in the instance's state dir, in `plugin-options.json` (owner-only), kept per plugin: a plugin removed and added again starts with none. They never reach the room server, a room or an export. Each turn writes them where Claude Code reads a `--plugin-dir` plugin's options: sensitive ones in the sandbox's `.credentials.json` as `pluginSecrets`, the others in `settings.json` as `pluginConfigs`, both rewritten every turn. A plugin with a required option unset and no default does not load: the turn runs without it, and the persona's Capabilities tab and the daemon page say "needs host setup". Before posting a turn, the daemon replaces each sensitive text value of the room, 4 characters or more, with `[redacted]` in the synthesis, the error, the documents, replies and notes, and the session, escaped forms included, and rewrites its local copy of the session the same way, so the next turn resumes without fetching it. JSON stays valid: the daemon redacts it string by string.

The approval sheet marks the websites of MCP servers that the host's egress allowlist leaves out, as the daemon saw it at the inspection. The daemon page lists them per plugin with an "Add to allowlist" button each, under the allowlist's own rules: no IP, no wildcard, no Anthropic host. Nothing is added without that press.

An export carries the room's plugins: link, ref, every version with its commit and inspection report, the snapshots the room still holds, and which personas have each one on. Option values stay on the host. The Export tab names the plugins from private repos, since their files go in the archive. An import pins each plugin at the same versions and loads none of them: the new instance's AI host checks each one, then approves it, even when it approves everything without asking. A version whose files the room had dropped, as a newer one replaced it, arrives as a record that never loads, and so does a refused or invalid one. The approval sheet says an imported version's files came from an archive, not from the repo, and the room links no commit for it. Update fetches the repo again, even at the same commit, once the new server can read it, or for a private repo, once the new host's git can.

"Save as starter" lists the room's plugins at the version in use, none checked, as for documents. A checked plugin goes in with its snapshot and stays on the personas that had it; one left out leaves them too. A room created from the starter gets it as version 1, which the AI host checks first; then the host approves it when it approves everything, and it loads at once otherwise, as for a starter's skills. A plugin the new room cannot take (past the instance's plugin size limit, the 10 plugins of a room or the room's quota) is left out, off its personas, with a line in the chat: the room is created anyway. The snapshots count in the starter's size against the storage quota, and in the new room's quota. Built-in starters carry no plugin.

### Triggers and chains

A persona runs on three triggers. Its button is the first. With "Speaks up every N answers" set in the sheet, it also runs after N completed turns of any persona since its own last turn; a failed turn of its own counts as that last turn, so a persona that keeps failing waits N answers before it tries again. The third is `@name`: a text message naming a persona, in any case and outside code, queues its turn as a press by the author, so only the host and the people they allow can call one that way, and only while the agent is online. A synthesis naming another persona queues that persona too. A persona naming itself runs again only with "Can follow up on its own" ticked. Each persona is queued once however many times it is named, and queued turns run in order like presses.

Turns that agents start, every N answers, the notes watcher or `@name` in a synthesis, are links of a chain. Above 0, the header shows the count against the room's budget, "auto 3/25" (25 by default), which the host and the people they allow set in the Personas sheet as the "Auto-turn limit". At the budget the next link is dropped, not queued (the notes watcher only waits, quietly): a line in the chat names who did not run, and a banner offers "Resume auto turns" and "Remove the limit". Dropping keeps a paused room from replaying a backlog of calls nobody saw once someone resumes it. A press, "Resume auto turns" or a text message that calls a persona starts the count over. Voice lines and other text do not. "Remove the limit" lets agents call each other without end, behind a red warning until someone restores the limit; the AI host's own cap still applies.

### Host cap and approvals

The host pays for every turn, so the host's daemon caps the model and effort personas run with. The cap comes from `GRILL_ROOM_MAX_MODEL` and `GRILL_ROOM_MAX_EFFORT`, or from the "Limit on models" form on the daemon page, which saves it in the instance's config dir and wins over the environment from then on. Delete that `settings.json` to go back to the environment's.

- Models rank `haiku` < `sonnet` < `opus` < `fable`. A full model id ranks with the family it names, so `claude-sonnet-5-5` is `sonnet` and a Mythos model is `fable`. An id naming no family ranks above all of them, so any cap lowers it. Efforts rank in `--effort` order: `low` < `medium` < `high` < `xhigh` < `max`.
- Model and effort clamp separately. A persona asking for `opus` and `max` under a `sonnet`, `high` cap runs at `sonnet`, `high`, and its synthesis says "requested opus · effort max → ran … (host cap)".
- A banner under the header lists every persona asking above the cap, with what it runs at. Everyone sees it; only the host answers. Approving lets that persona run as asked from its next turn, on the host's daemon only: the daemon's cap does not change. Refusing keeps it at the cap. Either answer is a line in the chat. An answer covers the exact model and effort it was given for: a persona asking for anything else above the cap shows in the banner again, and until then an approval still raises its cap up to what was approved.
- Answers belong to the daemon that hosted when they were given. After a hand-over, the new host's cap applies, the banner asks the new host again, and the old answers apply again if the old host takes the role back.
- With "Approve every new persona and persona change" ticked on the daemon page, or `GRILL_ROOM_APPROVE_ALL=true`, a member's new persona waits, greyed and unable to run, and any change of theirs to a persona waits too, in the same banner. Later changes to the same persona join its waiting request. The host's own changes apply at once, and removing a persona is never held, since it runs nothing. The mode follows the host's daemon even while it is offline. Waiting requests survive a hand-over and the new host decides them, whatever its own mode.

## Host daemon

`grill-room-daemon` runs on a participant's machine: Linux, macOS, or Windows inside WSL with the Linux build. It runs the agent with that participant's own Claude Code login, in a Docker sandbox.

```sh
make build
./bin/grill-room-daemon https://<host>/r/<room>
```

Or install it from the room page (see Distribution below).

The command runs the supervisor, one per machine: it holds a lock on its state dir. For each room server it serves (an instance), it starts a worker, `grill-room-daemon worker --instance <id>`, which holds the rooms' connections and sandboxes. The supervisor restarts a worker that crashes, with backoff, and its room reconnects with the stored token. Stopping the supervisor stops the workers, which remove their sandboxes. [docs/daemon-protocol.md](docs/daemon-protocol.md) has the protocol between the two. Running the command again with a room link while a supervisor runs hands the room to it over a local socket, then opens its page; running it again with no room is refused. A worker serves every room of its instance at once, each with its own connection and sandboxes.

The supervisor caps the turns running at once across all its instances and rooms: 2 by default, set under "Turns at once" on the page and saved in `supervisor.json`. Before a turn, its worker asks the supervisor for a slot. Turns past the cap wait in one queue, first in first out, and the room shows "queued (host busy)" until theirs starts. The page lists the rooms with their turns running and waiting, and the queue waits since start, to tune the cap.

The supervisor opens a page on `127.0.0.1` in the default browser; with none to open, as when it runs detached, it prints the link with the reason. `grill-room-daemon admin` gets a fresh link from the running supervisor, opens it and prints it; a plain second `grill-room-daemon` does the same. A tab bar, pinned at the top, splits the page into Rooms, AI accounts, Settings, Activity and Update; each tab is a deep link (`#accounts`) and shows its alerts as a badge. Rooms lists each server by its host name with its state and a `⋯` menu (the app's details, accepting unsigned binaries, cutting it off from the AI), then one row per room: its name linked to the room, its state (runs the AI, standby, paused, waiting for approval, disconnected), its AI account, and Pause hosting or Connect. A room's `⋯` has Remove this room. Pause keeps the room paired but tells it this computer cannot host, so another participant's app takes the AI host role (003b-AC5). Remove revokes this computer's token on the room server and deletes the room's token, cache and sandboxes here; if the server does not answer, "Remove anyway" removes it here only (003b-AC6). While a removal runs, Connect and a second Remove are refused. A room removed while its pairing waits for approval stores no token, and an approval that comes later is revoked at once (004b-AC14). Connect reconnects a disconnected room at once, or pairs again if the room revoked the token (003b-AC7). Settings shows Docker, the sandbox image and whether this computer can run the AI on one strip, then "This machine" (answers at once, days of history, start at login, sandbox CPU and memory) and "Per server" (its AI account, the model limits, approve-all, and the websites the AI may reach with each one's hits, the "Allow every website" switches and the requests the proxy refused), one Save per group; the allowlist and the switches apply at once. The Update tab holds the supervisor's signature, its update channel, the trusted dev keys and any update waiting. A "Start at login" box installs a systemd user unit (Linux and WSL), a LaunchAgent (macOS) or a scheduled task (Windows), and removes it again. The Rooms tab's "Add a room" takes a room link at any time, also while another room is connected, and hands it over as a second launch does. For each room this machine hosts, the Rooms tab also lists the room's requests to fetch a plugin, with Fetch and Decline, the plugins' options to set, and the websites their MCP servers reach with "Add to allowlist" (Room plugins, above). Any link inside a room works there, on the command line and in `install.sh`: the room page, its docs window or a document, with any query or fragment; a link with no `/r/<room>` is refused and the page says why. The room page's `⋯` › "Run the AI on my computer" gives the room's link to paste there, and the install when the server hands out a release. To pair, follow the page's link to the room, check that both pages show the same code, and press Approve; the line under Add a room then goes, a toast says the room paired, and its row shows its state: the room gives the daemon a token, which it keeps in the instance's `tokens.json`. The daemon only opens outbound connections: an SSE stream from the room plus a status POST every 15 s, and it reconnects with backoff.

State lives in one directory per instance, `instances/<id>/`, under three roots:

| | Config (`instance.json`, `settings.json`, `allowlist.json`; `supervisor.json`, `accounts.json` and `dev-keys/` at the root) | State (`tokens.json`, `plugin-options.json`, `plugin-cache/`, `plugin-fetch/`, lock, socket; `bin/`, `trust/` and `accounts/` at the root) | Cache (`workspace-cache/`) |
|---|---|---|---|
| Linux, WSL | `$XDG_CONFIG_HOME/grill-room` (`~/.config`) | `$XDG_STATE_HOME/grill-room` (`~/.local/state`) | `$XDG_CACHE_HOME/grill-room` (`~/.cache`) |
| macOS | `~/Library/Application Support/grill-room` | same | `~/Library/Caches/grill-room` |
| Windows | `%APPDATA%\grill-room` | `%LOCALAPPDATA%\grill-room` | `%LOCALAPPDATA%\grill-room` |

`GRILL_ROOM_DAEMON_STATE_DIR` puts all three in one directory. On first start, the supervisor migrates a single-room daemon's state dir (`GRILL_ROOM_DAEMON_STATE_DIR`, or `grill-room-daemon` beside the config root): each paired room moves to its server's instance with its token and workspace cache, the settings and allowlist are copied to each instance, `CLAUDE_CONFIG_DIR` is recorded as account `default` in `accounts.json`, and the old files stay in `legacy-backup-<date>` under the config root. Paired rooms keep working without pairing again.

The page listens on `http://127.0.0.1:47680/` (`GRILL_ROOM_DAEMON_ADMIN_PORT`), or on a random port when that one is taken. `grill-room-daemon admin` opens it in the browser. The page link carries a one-time code. The page trades it for a session token kept in `localStorage`, which only the page's own origin (`127.0.0.1` and its port) reads, and the daemon prints a fresh link in its terminal after each use. The app remembers the session for that port, as a sha256 in `admin-sessions.json` in the state dir, owner-only, for 30 days after its last use, so a bookmark of the page keeps working across restarts. General › Browsers signed in lists the remembered ones and signs one, or all, out. The token travels as a bearer header, never as a cookie, so another site, another localhost port included, sends none. The page refuses requests whose `Host` is not `127.0.0.1:<port>` or, for writes, whose `Origin` is not the page's own. The room links to the page from the room menu (the room's name) › Open my AI host app, from "Run the AI on my computer" and from Diagnostics; those links assume the default port. A remembered session is only as safe as that port: a program that takes `127.0.0.1:47680` while the app is down shares the page's origin and can read the token. On a computer shared with other accounts, set `GRILL_ROOM_DAEMON_ADMIN_PORT=0`: each start then picks a random port and remembers nothing.

The supervisor holds the Claude accounts, listed in `accounts.json`. Without that file, the only account is `default`: `$CLAUDE_CONFIG_DIR`, or `~/.claude`. The page adds and removes accounts of two kinds:

- A Claude Code config dir, read and never written. The page takes it as `~/…` or as an absolute path, stores it absolute and shows it as `~/…` under your home. It reads the macOS Keychain first (`security find-generic-password`, 3 s timeout, so a locked Keychain fails instead of hanging), then `<config dir>/.credentials.json`. The host's Claude Code keeps refreshing the token; the supervisor re-reads it when the file changes, when it expires and after an upstream 401. The page shows its expiry and warns 30 minutes before it.
- A `claude setup-token` token, pasted once and never shown again. It goes to the OS keyring (Keychain, Secret Service, Windows Credential Manager), or, when the keyring fails or takes over 5 s, to `accounts/<name>.token` in the state root: mode 0600, or on Windows a DACL that admits the current user alone. The token carries no expiry, so the page assumes a year from the day it was added and warns two weeks before. Its status comes from `POST /v1/messages/count_tokens`, which spends no inference: when added, every 15 minutes, a minute after upstream refuses a proxied request, and on "Check now". Only that probe marks the token refused.

Each instance has an account, `default` unless the page picks another, and each room may use its own. Each account has its own bearer-swap proxy, in the supervisor. A worker gets each room's proxy address and a dummy bearer of its own, never a token, and its environment loses every `CLAUDE_*` and `ANTHROPIC_*` variable. A room moved to another account loses its bearer for the old one. The proxy counts each worker's requests, shown on the page. "Cut it off from Claude" revokes the worker's bearers at every proxy and ends its running turns with "the host cut this agent off from Claude for now" in the room; the room sees the agent offline until "Let it use Claude again". The room never sees an account name, a config dir or this machine's name: it shows "Alice holds the agent(s)".

The sandbox holds no credential. It sits on an `--internal` Docker network whose only other members are a socat relay to its account's proxy and the egress proxy, below. The proxy replaces the sandbox's dummy bearer with the account's token. It forwards only `POST /v1/messages`, `POST /v1/messages/count_tokens` and `HEAD /api/hello`, and answers 403 to anything else: code in the sandbox can read the dummy bearer, and without the allowlist it could spend the real token on any Anthropic API (spike S16). It listens on the default bridge gateway, or on `127.0.0.1` under Docker Desktop. The daemon writes a dummy `.credentials.json` and an `oauthAccount` stub before every turn and sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false` (spike S3). Containers, networks and volumes carry the `grill-room-daemon` label, plus `grill-room-root` (a hash of the supervisor's state dir) and `grill-room-instance`, and are removed when the sandbox closes. A supervisor killed with its workers leaves them behind: the next one removes everything labelled with its own state dir at start, and never touches another's. To check a new room plugin version, the host's daemon also runs a throwaway container from the sandbox image, with no network and a read-only root, for at most 60 s ([docs/agent-workspace.md](docs/agent-workspace.md), Plugin inspection).

The image has `python3` with a venv on `PATH` (`/home/agent/.venv`, layered on Debian's openpyxl, pandas, python-docx, pypdf and matplotlib, plus python-pptx from PyPI), `uv`, `pip`, `node` 24 with `npm`, `pandoc`, `jq`, `yq`, `rg`, `git` and `curl`. No LibreOffice. The base, pandoc and uv images are pinned by digest; Node, yq and python-pptx are checked against sha256 sums the Dockerfile pins; the Claude Code installer checks its download against its release manifest. It runs as the non-root `agent` user on a read-only root filesystem; the home and `/workspace` are volumes, so `uv pip install`, `pip install` and `npm install` work there. It weighs 1.26 GB, up from 455 MB before the tools: Claude Code 257 MB, the Python stack about 300 MB, pandoc 147 MB, Node 138 MB.

Tools reach the Internet through an egress proxy, a squid container per sandbox started from the same image. Squid sits on the sandbox's internal network as `egress` and on a bridge of its own that routes out. The sandbox gets `HTTP_PROXY` and `HTTPS_PROXY` (and lowercase) pointing at it, which uv, pip, npm, git and curl follow, and `NO_PROXY=proxy,localhost,127.0.0.1`, so Claude Code's own traffic still goes to the bearer-swap proxy and never through squid. Squid denies `.anthropic.com`, `.claude.ai` and `.claude.com` first, except the two documentation hosts `code.claude.com` and `support.claude.com`, then anything but `CONNECT` to port 443, then any host off the allowlist. It does not intercept TLS, so an allowed host gets the whole tunnel. The default allowlist is `pypi.org`, `files.pythonhosted.org`, `github.com`, `codeload.github.com`, `raw.githubusercontent.com`, `objects.githubusercontent.com`, `registry.npmjs.org`, `code.claude.com` and `support.claude.com`. A server whose list was saved before the docs hosts existed keeps its list: the host adds them by hand on the Network tab.

"Allow every website", under the list, lets any domain name through on port 443, after a confirmation with a red warning. Squid then still refuses Anthropic's hosts, IP addresses, and names that resolve to the host's own networks (loopback, private, CGNAT, unique-local) or to link-local addresses. A domain on the list keeps working whatever it resolves to. A second switch under it, "Also allow the local network and IP addresses", lifts the IP and private-network refusals, behind a stronger warning: agents can then reach the router, a NAS or this computer on port 443. Link-local addresses, `169.254.0.0/16` and `fe80::/10`, stay refused at every level, as cloud metadata answers on `169.254.169.254`. Every request squid sees during a turn goes to the daemon log as an `egress` line with the room, the persona, the host and the verdict, and the allowlist table adds the hosts reached that no entry covers. Each turn's `settings.json` sets `skipWebFetchPreflight`: Claude Code's WebFetch otherwise asks `api.anthropic.com` about every domain first, which squid refuses, so every fetch failed.

When a turn ends, each domain its sandbox was refused on port 443 shows in the room's chat: "Grill tried to reach example.com (blocked)". A second refusal while the line is undecided counts on it. The AI host gets "Allow for this room" and "Allow everywhere" on the line, and the website waits in the banner under the room's header, with "Dismiss" too, until it is decided; everyone else reads who can allow it, and can let the room's admins allow websites for that room only, in Room settings › Websites; the choice resets when the AI host role moves, and so do approvals the previous host's app had not applied yet. The host's app applies the approval, then the line says who allowed what, and the server's audit log has an `egress.allow` entry. A room's own websites sit beside the server's in the daemon page's table, with a scope column ("Every room" or the room's name) and who allowed each one in its tooltip. Removing one there applies at once and tells the room. A room's list holds 100 domains, follows the server list's rules, and goes with the room when the daemon page removes it. IP addresses, Anthropic hosts and requests on other ports stay on the daemon page only.

On Linux with Docker Engine, a request to a public name off the list waits instead of failing at once, while the host decides: squid asks the daemon through a socket mounted into that sandbox's egress proxy only, the website shows in the banner straight away, and an approval within the hold time (45 s by default, 30 to 60 in the daemon page's settings) lets the same answer reach it. A dismissal, no answer in time, or no host or delegated admin in the room refuses it as before. Anthropic hosts, link-local, private and IP destinations are refused without asking, and requests outside a turn too. Measured: WebFetch survives a 45 s hold; curl waits; pip retries on its 15 s timeout. The sockets live in a folder of the user's runtime folder (`$XDG_RUNTIME_DIR`), private to them.

claude.ai connectors (calendar, mail, drive) reach a room only when the host turns them on, room by room, on the daemon page: Rooms › a room › Connectors. The supervisor lists the room's account's connectors with the account's login, on the host, and reads each one's tools without calling any. A turn in a room with connectors on gets one `--mcp-config` entry per connector, pointing at the account's proxy with a bearer of that room's own, and `ENABLE_TOOL_SEARCH=true`. The proxy forwards that bearer only to `POST /v1/mcp/<id>` of the connectors on for the room, with the account's token swapped in; anything else gets 403. A connector's tools without `readOnlyHint` go into `--disallowedTools` unless the host ticks "Allow actions" for it. Turning one off refuses its next request, mid-turn included. A connector whose claude.ai login lapsed shows "needs login on claude.ai"; its 401 leaves the account's token alone. Each change is a chat line and an audit entry in the room, and Room settings › Websites and connectors lists the ones on.

The host edits the list on the daemon page: one domain per entry, or a leading dot (`.example.com`) for a domain and its subdomains. The page refuses wildcards, IP addresses, ports, URLs and Anthropic hosts, and drops an entry a leading-dot entry already covers, which squid would refuse. The list and the switches are saved in the instance's `allowlist.json` and the running squid reloads at once. Below it the page lists the last 50 requests squid refused in the instance's sandboxes, with host and time, read from squid's access log; the list empties when the sandbox goes.

The sandbox gets 2 CPUs and 4 GiB and squid 0.5 CPU and 256 MiB by default, swap included, so a runaway script is killed instead of paging the host. The four `GRILL_ROOM_*_CPUS` and `*_MEMORY` variables below change that; `0` lifts a limit.

When someone presses a persona's button, the room hands the turn to the host's daemon. The daemon fetches the job and the workspace tar, clears the sandbox's `/workspace` and unpacks the tar there. If the room's copy of the session differs from the local one, it fetches the room's copy. Then it runs `claude -p` with the prompt on stdin, the persona's text as an appended system prompt file, its `--model` and `--effort`, `--resume` when the room has a session for that persona, and one `--plugin-dir` for its skills and each room plugin it has on, and posts back the changed files, the final answer and the session bytes added. [docs/agent-workspace.md](docs/agent-workspace.md) has the workspace layout and the prompt contract. A turn is cancelled after the room's turn timeout, counted from when it leaves the host's queue. A room's first sandbox is named from the supervisor's state dir and the room, so a restarted worker replaces what a crash left; a turn running beside another gets a sandbox of its own, `<name>-1` and on. They share the room's workspace cache.

The sandbox image comes from the room server. When the server advertises a digest-pinned image (`GRILL_ROOM_SANDBOX_IMAGE` on the server), the daemon pulls it by digest. When it advertises none, or the pull fails, for instance on a registry that wants a login, the daemon builds the Dockerfile embedded in its binary and tags the result `grill-room-sandbox:local-<hash of the Dockerfile>`, so it builds once per Dockerfile change. The page shows the pull or build progress. Until the image is ready, the daemon tells the room it cannot host.

#### Worker binaries and signatures

Each instance's worker runs the daemon version its room server hands out. When that is the supervisor's own version, or the server hands out none, the worker runs the supervisor's binary. Otherwise the supervisor reads `/api/daemon/version`, downloads the binary for its OS and architecture and its sigstore bundle, and runs it only if all of these hold:

- the download matches the sha256 the server publishes;
- sigstore-go verifies the bundle: a certificate for this repository's `release.yml` on a semver tag, issued by GitHub Actions, logged in Rekor ([docs/release.md](docs/release.md#signing-identity)), whose tag is the version served; or a signature by one of the trusted dev keys;
- the file is an executable for this OS and architecture;
- the version is v0.0.2 or later, the first release that runs as a worker.

Otherwise the worker stays stopped and the instance list shows why, as does the log. The binary and its bundle are kept in `bin/<version>/` under the state root, one copy per version, and verified again before every start, offline included. A version no instance runs any more is deleted at start and whenever an instance changes version. When a worker reports that its room server now hands out another version, the supervisor restarts it on that version.

Verification works offline with the sigstore trusted root embedded in the binary. Online, the supervisor refreshes it through TUF when it verifies a binary, at most once a day (cache in `trust/tuf` under the state root) and keeps the last good copy in `trust/trusted_root.json`. When TUF is unreachable it uses that copy, else the embedded one, and tries TUF again an hour later. The page says which root is in use.

Dev builds signed by `make dev-release` run once their cosign public key is trusted: paste it under "Trusted dev keys" on the page, or drop it in `dev-keys/<name>.pub` under the config root. Adding a key restarts the refused workers; removing one restarts the workers running a binary it signed.

Each instance also has an "accept unsigned binaries" toggle, off by default, for testing builds nobody signed. Switching it on takes the instance's host typed exactly as in its URL. While it is on, a red banner and a badge stay on the page and every worker start logs `worker_accepts_unsigned`. The binary must still match the published sha256 and this platform.

Worker log lines and stderr reach the supervisor's terminal re-encoded: the supervisor sets their `instance` field and escapes control and Unicode format characters, so a worker binary cannot drive the terminal.

#### Supervisor updates

The supervisor updates itself from GitHub releases by default: it reads `releases/latest/download/VERSION` at start and every 6 hours, and the page offers "Update and restart" for a newer version. The other channel, "the version an instance serves", follows one instance and offers whatever version it hands out, older ones included, under that instance's rules (dev keys, accept unsigned). It checks again as soon as that instance moves to another version. Nothing updates without that click. The supervisor downloads the binary next to its own and checks it like a worker binary. Only then does it rename it over the running binary and keep the bundle beside it as `<binary>.sigstore.json`. It then stops its workers, which remove their sandboxes, and execs the new version, which reconnects to the same rooms. The new version binds the page's port again and keeps its sessions, handed over in an owner-only file of the state dir, so the open tab says "Updating…", reconnects by itself and reloads to run the new version's page. It prints a fresh link either way, and opens it only if that port was taken meanwhile. A binary named after its version, `grill-room-daemon-v0.0.3`, becomes `grill-room-daemon` at the update, and a login item follows it. On a failed check it keeps the current binary and shows the reason. The binary's directory must be writable by the user, as `~/.local/bin` is.

Next to its version, the page says whether the running supervisor is project-signed. It checks its own binary against `<binary>.sigstore.json`, or against the release's bundle on GitHub. A version that is not a release, or that GitHub does not have, shows "dev build"; a binary its bundle does not match shows "NOT project-signed".

`grill-room-daemon check` checks Docker and account `default`, builds the embedded sandbox image unless one is pinned, runs `claude -p --model haiku "say ok"` in a throwaway sandbox, checks that only the two proxies are reachable and that the egress proxy refuses `api.anthropic.com`, and counts the real token's occurrences in the container, its volumes and its inspect output. It spends one Claude request.

### Distribution

The room server hands out the daemon itself. `make release` cross-compiles it for linux, darwin and windows, amd64 and arm64 (static, `-trimpath`, version stamped; the windows builds end in `.exe`), and writes a sha256 file per binary plus `VERSION`. The server image builds the same release into `/daemon`, unsigned, or ships a signed one with its bundles (`docs/release.md`). These routes need no token:

| Route | |
|---|---|
| `GET /install.sh` | the installer |
| `GET /download/grill-room-daemon-<os>-<arch>[.exe][.sha256]` | a binary, or its `sha256sum` line |
| `GET /download/grill-room-daemon-<os>-<arch>[.exe].sigstore.json` | the binary's cosign bundle, when the release is signed |
| `GET /api/daemon/version` | `{"version", "sha256": {"<os>-<arch>": "<hex>"}, "bundles": {"<os>-<arch>": "/download/<binary>.sigstore.json"}, "sandbox_image"}`; `bundles` lists only signed targets |

The room page's `⋯` menu has "Run the AI on my computer". It guesses the visitor's OS and CPU (Chromium reports the CPU, Safari and Firefox do not, so both stay editable), links the matching binary with its sha256, and shows the one-liner:

```sh
curl -fsSL https://<host>/install.sh | sh -s -- https://<host>/r/<room>
```

`install.sh` is POSIX sh. It picks the build from `uname` (WSL gets the Linux one, a Rosetta shell the arm64 one), downloads it from the host in the room URL, and checks it against the published sha256. With `cosign` on the PATH, it also checks the binary's sigstore bundle against the project's release workflow identity (docs/release.md), and refuses a build whose bundle is missing or does not verify; without cosign it says the signature was not checked. Then it moves it into `~/.local/bin` and starts it with the room URL, which opens the pairing page. On a mismatch it installs nothing. It accepts plain `http` for `localhost` and `127.0.0.1` only.

On macOS, a binary downloaded through the browser carries the quarantine flag, and Gatekeeper refuses it because it is not notarized. Make it executable and clear the flag (on Intel, the file ends in `-darwin-amd64`); with macOS picked, the panel shows this command for the chosen CPU:

```sh
chmod +x ~/Downloads/grill-room-daemon-darwin-arm64 && xattr -d com.apple.quarantine ~/Downloads/grill-room-daemon-darwin-arm64
```

The one-liner needs neither: `curl` sets no quarantine flag.

## Local dev with docker compose and traefik

The dev setup expects a traefik on the machine that serves `*.<dev-domain>` with a valid wildcard certificate and watches a file-provider rules directory. Copy `.env.example` to `.env` and fill in `DEV_DOMAIN` and `TRAEFIK_RULES_DIR`.

```sh
make dev-up     # renders deploy/local/traefik-grill-room.yaml into the rules dir, starts compose
make dev-down   # removes the rule, stops compose
```

The room server's store is the `postgres` service, data in the `grill-room-pg` volume. The server no longer reads the old SQLite `grill-room-data` volume; `grill-room db copy` moves its data (see Copying a SQLite database). Compose also runs mailpit, which catches the magic link mails; its inbox is at `http://127.0.0.1:8025` (`MAILPIT_PORT`). `make dev-up` publishes the app port and LiveKit's 7880 and 5349 on the docker bridge gateway only, which is where traefik's `host.docker.internal` points, so the plain-HTTP ports stay off the LAN. The room is then at `https://grill-room.<dev-domain>/`, LiveKit signalling at `livekit.<dev-domain>` and TURN at `turn.<dev-domain>`. Compose needs the LiveKit key pair and the STT token in `.env`. With `GRILL_ROOM_ADMIN_TOKEN` set there, that is the admin token; otherwise read the generated one with `docker compose logs grill-room | grep admin_token_generated`.

## Lab deployment on Kubernetes

`deploy/k8s/` holds plain manifests for the room server, LiveKit and the STT worker, applied with kubectl. There is no GitOps and no Helm. The templates carry no domain, registry, digest or secret. `make k8s-render` fills them from `.env` into `deploy/k8s/out/`, which is untracked and readable by its owner only.

The cluster needs:
- traefik as the `traefik` IngressClass, with its CRDs (`IngressRouteTCP`) and a `websecure` entrypoint on 443;
- a certificate for the three hostnames in traefik's default TLS store, since the routes name no secret;
- a PostgreSQL 16 or newer database with `C` collation, owned by its own login role (see Run), reached directly on the primary: no pooler, as `LISTEN` and the advisory locks need one session. A Secret `K8S_PG_SECRET` in the namespace holds the role as keys `username` and `password`; the `.env` keys `K8S_PG_*` name the host, port, database, namespace and `sslmode` (`.env.example`);
- amd64 nodes for the room server and the worker, one of them with 2 free CPUs and 3 GiB for the worker, and two for the room server's pods to survive a node drain;
- a namespace you create beforehand, with pull access to your registry for its default service account.

```sh
make k8s-push VERSION=v0.8.0 DAEMON_DIST=<release dir>  # from the tag: server, stt and tts; prints their .env lines (docs/rollout.md)
export KUBECONFIG=<lab kubeconfig>
make k8s-apply                   # renders, applies to K8S_NAMESPACE (default grill-room), waits for the rollouts
make k8s-delete                  # removes everything k8s-apply created; the database stays
```

The targets refuse to run without `KUBECONFIG` set, so the default kubeconfig is never used by accident. The namespace is left alone: delete it yourself.

What gets deployed, with `<domain>` standing for `K8S_DOMAIN`:

| Host | Route | Backend |
|---|---|---|
| `grill-room.<domain>` | Ingress, HTTPS | room server, port 7680 |
| `grill-room-livekit.<domain>` | Ingress, HTTPS | LiveKit signalling, port 7880 |
| `grill-room-turn.<domain>` | IngressRouteTCP, `HostSNI`, TLS terminated by traefik | LiveKit TURN, plain on 5349 (`turn.external_tls`) |

- The room server runs two replicas on PostgreSQL, through `GRILL_ROOM_DATABASE_URL` with `PGUSER` and `PGPASSWORD` from `K8S_PG_SECRET`. A rollout replaces one pod at a time (`RollingUpdate`, `maxUnavailable: 0`, `maxSurge: 1`), and a PodDisruptionBudget (`minAvailable: 1`) keeps one up through a node drain. The pods spread over nodes when they can; a one-node cluster still runs both. No session affinity: any pod answers any request. [docs/rollout.md](docs/rollout.md) is the rollout runbook and its check, `make rollout-watch`.
- Each server pod has its own disks, all `emptyDir`: exports and imports stage on 2.5 GiB (two 1 GiB imports at once plus margin), and the init container fetches the on-device model files into 1 GiB, about 440 MB at each pod start. A pod whose download failed serves no model files, so device transcription fails for the browsers whose requests reach it, until the pod is replaced (`kubectl delete pod <pod>`) and its init container fetches them again. Probes hit `/healthz`, and `/metrics` is on 7681.
- Releases before two replicas kept the model files on a `grill-room-models` volume. `make k8s-apply` leaves it in the cluster: delete it after the first rollout, `kubectl -n <namespace> delete pvc grill-room-models`.
- The `grill-room-data` volume held the SQLite database of before the cutover. Its object is gone from `deploy/k8s/room.yaml`: once the cutover's rollback window ends, delete it, `kubectl -n <namespace> delete pvc grill-room-data`.
- LiveKit exposes no UDP. Browsers relay through TURN/TLS on 443. `allow_restricted_peer_cidrs` lists only the pod's own IP, where the relay hands media to the SFU.
- The STT worker requests 2 CPUs and may burst to 4, with 3 GiB as request and limit: two parakeet engine processes of 2 threads (spike S10d). One pod serves every room, about four people talking at once. It updates with `Recreate`: no lab node has 2 CPUs free for a second worker beside the old one, so transcription stops for the minute a new pod takes to load the models.
- Switching the STT engine back to faster-whisper is one command, in [docs/lab-checklist.md](docs/lab-checklist.md) (STT engine rollback).
- `make k8s-monitoring` applies the STT queue alert and the scrapes of the STT worker, the `tts` pod and the room server (`deploy/monitoring/`) for a cluster running the VictoriaMetrics operator; `make k8s-monitoring-delete` removes them. `K8S_MONITORING_NAMESPACE` (default `monitoring`) is where vmagent runs.
- `make k8s-autoscale` lets KEDA scale the `tts` pod between 0 and 1 on `grill_room_tts_demand` (`deploy/autoscale/tts.yaml`), read from the Prometheus API at `K8S_PROMETHEUS_URL`; it needs KEDA and `make k8s-monitoring`. Off by default; `make k8s-autoscale-delete` puts one pod back, always on. `make k8s-apply` sets the pod back to 1 until KEDA's cooldown.
- Every pod runs as non-root with a read-only root filesystem, no service account token and no service links.
- A default-deny NetworkPolicy blocks everything, then one policy per flow opens DNS, traefik to the room server and LiveKit, the worker to both, the room server to LiveKit's API, to PostgreSQL (`K8S_PG_PORT` in `K8S_PG_NAMESPACE`) and, for Web Push and the OIDC provider, to TCP 443 anywhere (the server itself posts only to `GRILL_ROOM_PUSH_HOSTS` and the endpoints of the issuer's discovery document), media between LiveKit and the worker, the worker's traces to the cluster's OpenTelemetry collector, and, with `make k8s-monitoring`, vmagent to the metrics ports of the room server, the worker and the `tts` pod (a Kyverno policy there injects `OTEL_EXPORTER_OTLP_ENDPOINT` into every pod).
- The Secret `grill-room` comes from the same `.env` keys compose uses.
- With `GRILL_ROOM_SMTP_ADDR` and `GRILL_ROOM_SMTP_FROM` in `.env` (plus `GRILL_ROOM_SMTP_USERNAME` and `GRILL_ROOM_SMTP_PASSWORD`, kept in the Secret, for a relay that wants a login), the room server mails magic links; the `room-smtp` NetworkPolicy opens TCP `K8S_SMTP_PORT` (default 1025; 587 for an external relay) to the namespace `K8S_SMTP_NAMESPACE` (default `mailpit`), where an in-cluster relay runs, and to any address.
- With `GRILL_ROOM_OIDC_ISSUER`, `GRILL_ROOM_OIDC_CLIENT_ID` and `GRILL_ROOM_OIDC_CLIENT_SECRET` in `.env` (the secret kept in the Secret), the instance is restricted; `GRILL_ROOM_OIDC_SCOPES`, `GRILL_ROOM_OIDC_MEMBER_GROUP`, `GRILL_ROOM_OIDC_GROUPS_CLAIM`, `GRILL_ROOM_OIDC_ADMIN_GROUP`, `GRILL_ROOM_OIDC_REVALIDATE` and `GRILL_ROOM_OIDC_NAME` pass through as set. Left empty, they render empty and restricted mode is off. Turn it on in two rollouts: first the image that knows these variables, then `GRILL_ROOM_OIDC_ISSUER` and the rest, as pods still on an older image would enforce none of it. `make k8s-render` refuses a double quote or a backslash in any of them, a secret outside `[A-Za-z0-9._~+/=@-]`, and an issuer on a port other than 443, the only one the `room-push` policy opens.

`make e2e-lab` runs a whole session against the deployment through its public hostnames, with two participants, an upload, an annotation, audio and a voice line. Audio runs twice, once forced through TURN/TLS and once with default ICE. One agent turn runs with a real daemon on this machine and haiku, at most six Claude requests. [docs/lab-checklist.md](docs/lab-checklist.md) is the manual check with a participant outside the LAN.

`scenarios/` replays scripted sessions against the deployment, or any instance, with synthetic voices and real daemons, and reports on each assertion: a dark-mode grill, a two-persona chain, a long session and a host hand-over. It prints the Claude request budget before it starts. [docs/scenarios.md](docs/scenarios.md) has the file format and the voice licenses.

CI also runs a flake gate, `tools/flake-gate.sh`: on Linux and Windows, the Go tests in every test file a change adds or edits run five times with the race detector, and the e2e specs it adds or edits run three times each (`make e2e-repeat SPECS=…`), against the PR's base. Running the `ci` workflow by hand (`gh workflow run ci.yml --ref <branch>`) runs the full gate: every Go package five times with the race detector, on Linux and Windows, and every e2e spec three times. `e2e-twopod` runs its spec three times in its own job, as the gate does for a changed spec. `e2e-keycloak` runs in its own job on pull requests and `feat/**` pushes whose changes touch the OIDC code, the reauth or admin page scripts, the e2e oidc or keycloak stack, the shared e2e files, the Makefile or the workflow, on every push to develop and on a manual run; it uploads the test results when it fails.

### Writing stable tests

- Assert on state, never on elapsed time. In Go, inject the clock. In Playwright, wait on a locator or `expect.poll`.
- A `time.Sleep`, `waitForTimeout` or fixed `setTimeout` in a test carries a comment saying why: a poll bounded by a deadline, or a wait on a process with no clock to move.
- Every network or IPC call in a test has a deadline.
- Names are unique per test (rooms, pipes, sockets, containers), and the test removes what it created.
- Before acting, wait for the state the action needs. A page that shows "connected" may be ahead of the server that will accept the action.
- A test that fails once in CI is a bug. Find the cause, fix it in the test or the product, and write the cause in the commit body. Rerunning until green is not a fix.
- Repeat runs happen in CI, never on a workstation.
- A spec whose daemon runs agent turns goes in `sandboxSpecs` in `e2e/playwright.config.js`. Chrome fails the requests it is opening whenever the host's interfaces change, and each sandbox adds and removes Docker networks, so those specs run one at a time, after the others.
